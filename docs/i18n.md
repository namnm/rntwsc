# I18n

Works on all variants: server, browser, native, web (Vite SPA). No extra setup needed.

## Usage

```tsx
import { useTranslation } from '@/i18n'

export const MyComponent = async () => {
  const t = await useTranslation('home')
  return <Text>{t('greeting')}</Text>
}
```

## Add a translation key

Add the key to each language file under playground/app/src/i18n/labels/lang/namespace.json:

```json
// en/home.json
{ "greeting": "Hello" }

// fr/home.json
{ "greeting": "Bonjour" }
```

## Add a namespace

1. Create labels/lang/namespace.json for each language.
2. Register in playground/app/src/i18n/labels/index.ts:

```ts
export const labels = {
  en: { home: enHome, settings: enSettings },
  fr: { home: frHome, settings: frSettings },
} as const
```

TypeScript infers valid Namespace values automatically from the labels shape.

## Add a language

Add an entry to languages in playground/app/src/i18n/config.ts and create the label files:

```ts
export const languages = [
  { locale: 'en-US', nativeName: 'English' },
  { locale: 'fr-FR', nativeName: 'Français' },
] as const
```

nativeName is display only - it is what the language switcher shows for each option, in that language's own script, and is never used for locale matching or routing.

## Language switcher

Drop I18nSwitcher anywhere - it renders locale links on web, pressable buttons on native:

```tsx
import { I18nSwitcher } from '@/i18n/i18n-switcher'

export const MyPage = async () => (
  <>
    <Content />
    <I18nSwitcher />
  </>
)
```

## Direction (RTL)

Direction is derived from the current language, not stored per language entry. A language is
considered right-to-left if its 2-letter code is in the `rtlLangs` set in
packages/core/i18n/config.ts (ar, he, fa, ur, yi, ps, sd, dv). Adding a language such as `ar-AE`
to `languages` in playground/app/src/i18n/config.ts is automatically picked up as RTL - no
extra flag needed.

```tsx
import { useCurrentDirection, useIsRtl } from '@/i18n'

export const MyComponent = async () => {
  const dir = await useCurrentDirection() // 'ltr' | 'rtl'
  const rtl = await useIsRtl()
  return <Text>{rtl ? 'RTL' : dir}</Text>
}
```

On web, `dir` is set on the root `<html>` element (playground/app/src/app.tsx). This alone
flips any layout using `flex-row` - the CSS spec defines `row` relative to the writing mode's
inline axis, so it mirrors automatically under `dir="rtl"`, on both web and native (native
mirrors `flexDirection: 'row'` once `I18nManager.forceRTL()` is set, see
packages/core/i18n/index.native.tsx). `gap-*` is direction-agnostic and is preferred over
margin/padding for spacing between flex-row siblings for this reason.

What does not auto-mirror, on either platform, is anything using a physical Tailwind
utility - `left-*`/`right-*`, `pl-*`/`pr-*`, `ml-*`/`mr-*`, `rounded-l-*`/`rounded-r-*`, and
direction-implying icons (back/prev/next chevrons). Those need an explicit `await useIsRtl()`
check to pick the correct class or icon per direction - see
packages/core/components/button/index.tsx (group-join corners),
packages/core/components/button/group-overlap-class-name.ts (button group border overlap),
packages/core/components/switch/index.tsx (thumb position via translate-x),
packages/core/components/input/index.tsx (prefix/suffix side and padding),
packages/core/components/drawer/index.tsx (`side: 'start' | 'end'`), and
packages/core/components/date-picker/index.tsx (prev/next chevrons) for examples.

## Internals

Platform entry points in packages/core/i18n/:

| File              | Used by            | How                                                                                                                         |
| ----------------- | ------------------ | --------------------------------------------------------------------------------------------------------------------------- |
| index.tsx         | Server components  | Async hooks reading the x-i18n-locale header, wrapped in cache()                                                            |
| index.browser.tsx | Browser components | Sync hooks parsing the locale from the URL pathname                                                                         |
| index.native.tsx  | React Native       | Thin wrapper around shared.tsx; also forces I18nManager's RTL flag on init, exports I18nProviderNative and initI18nNative() |
| index.web.tsx     | Vite SPA           | Thin wrapper around shared.tsx; exports I18nProviderWeb and initI18nWeb()                                                   |
| shared.tsx        | native + web       | The actual i18next-backed hooks and provider both variants above re-export                                                  |

`I18nManager.forceRTL()` only fully takes effect after an app reload. index.native.tsx still calls it as soon as the resolved language is known, so `I18nManager.isRTL` is in sync with the persisted locale by the next launch, even though the current session's layout does not re-mirror until then.

I18n is initialized once at startup by playground/app/src/polyfill/init-i18n.ts:

```ts
import { initI18n } from '#/core/i18n/config'
import { locales } from '@/i18n/config'
import { labels } from '@/i18n/labels'

initI18n(locales, labels)
```

This file is imported at the top of each platform's polyfill entry.

On web (Next.js), switching locale navigates to a locale-prefixed URL; middleware sets the locale cookie. On native and on a Vite SPA (the "web" variant), i18next is called directly and the locale is persisted through storage (see packages/libs/storage) - AsyncStorage works on both, since @react-native-async-storage/async-storage has its own web implementation, so no separate localStorage polyfill is needed for the Vite SPA case. On a Vite SPA specifically, since navigation state is real react-navigation state (see navigation.md), playground/app/src/app.web.tsx's `linking` config syncs i18next's language from the URL's locale segment on navigation, since there is no server to set a cookie from the URL.

The framework exports untyped functions (useTranslationUntyped, isValidLocaleUntyped) so each app wraps them with its own strict Locale and Namespace types in playground/app/src/i18n/index.ts, without coupling the core package to any specific locale set.

### Label validation

`node ./devtools check-i18n-labels` (packages/cli/check-i18n-labels) scans playground/app/src
for `t('key')` usage and validates it against the en label set. It reads en/*.json directly
instead of importing playground/app/src/i18n/labels, since that module's shape has an extra
per-language level that the validator's Labels type doesn't expect. Monorepo-internal only -
a generated project has no playground to check.
